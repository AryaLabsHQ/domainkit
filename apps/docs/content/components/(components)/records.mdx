The records namespace renders the requirements your product supplies, plus the readiness a
`Verify` controller observed. It reads no DNS of its own.

## Table

`Records.Table` renders one row per requirement: type, name, value, purpose, and a status column
when `readiness` is present. Values carry a copy action.

| Prop        | Type                             | Required | Means                     |
| ----------- | -------------------------------- | -------- | ------------------------- |
| `records`   | `ReadonlyArray<DnsRecord.Model>` | yes      | The requirements to show  |
| `readiness` | `Verify.Readiness \| null`       | no       | Adds the status column    |
| `caption`   | `string`                         | no       | A caption above the table |

The table's leaf parts (`Header`, `Body`, `Row`, `Head`, `Cell`, `Caption`, `Value`, `Purpose`) are
exported, so a host can assemble its own table from the same parts and keep the styling hooks.

## Zone file

`Records.ZoneFile` renders the same records as zone-file lines with copy and download actions.
`Records.toZoneFile(records)` returns the text on its own, and `Records.downloadZoneFile` triggers
the download; both run only from a user action, so the component renders on the server.

## Helpers

| Helper                     | Returns                                                   |
| -------------------------- | --------------------------------------------------------- |
| `Records.identity(record)` | A stable key for a requirement: type, name, and data      |
| `Records.statusOf`         | One requirement's status out of a readiness row           |
| `Records.useCopy(value)`   | A copy controller with a `copied` flag that resets itself |

## Accessibility

Copy and download controls carry action-specific labels. Keep them when supplying your own icons,
and keep the header cells when assembling a table from the leaf parts.
