`dns-status` is a small readiness badge. It renders the status you give it; it does not observe DNS
or decide what a status means for your product.

<Component path="registry/dns-status" />

## Installation

```package-install
npx shadcn@latest add https://domain-kit.dev/r/dns-status.json
```

## Usage

`status` picks both the tone and the default label, so the four requirement statuses need nothing
else.

```tsx
<DnsStatus status="satisfied" />
<DnsStatus status="missing" />
<DnsStatus status="mismatch" />
<DnsStatus status="unknown" />
<DnsStatus tone="warning">Checking again in 5 minutes</DnsStatus>
```

## API

| Prop       | Type                                                  | Required | Description                            |
| ---------- | ----------------------------------------------------- | -------- | -------------------------------------- |
| `status`   | `"missing" \| "mismatch" \| "satisfied" \| "unknown"` | no       | Picks the tone and the default label.  |
| `tone`     | `"danger" \| "neutral" \| "success" \| "warning"`     | no       | Overrides the tone the status implies. |
| `children` | `ReactNode`                                           | no       | Replaces the default label.            |

`dnsStatusTones` and `dnsStatusLabels` are exported, so the copied file is where you change the
wording or the colour of a status.

`DnsStatus` also accepts shadcn `Badge` props and `className`, except `variant`, which the component
controls so the tone stays legible.

Keep the evidence in visible text. Colour is extra information and must never be the only way your
interface says a record is missing, mismatched, or unchecked.

## Boundary

The statuses match what [verification](/docs/core/verification) reports per requirement. Observing
DNS and deciding what readiness means for your product both stay in the host application; the
[records table](/components/registry/records-table) reports the first for you.
