`records-table` lists the records your product needs at a domain, one row each, with the type, the
name, a copy control for the value, and where the record stands.

<Component path="registry/records-table" />

## Installation

```package-install
npx shadcn@latest add https://domain-kit.dev/r/records-table.json
```

## What a row says

A plan still awaiting its apply gets a column of its own saying what it will do: add the record,
leave it, or nothing while it is blocked. The status column beside it is always what the observers
read back. `Records.standingOf` hands the row both facts, so the table renders each column from the
one that is about it.

A blocked record gets a second row under it naming what is in the way and what to do about it, both
from the message catalog.

Here an A record already sits on the tracking host, so its CNAME is a conflict. The plan approves
the records that can be added and leaves the blocked one for the customer to fix at their provider.

## API

| Prop     | Type          | Required | Description                                    |
| -------- | ------------- | -------- | ---------------------------------------------- |
| `flow`   | `Domain.Flow` | yes      | The flow whose requirements the table renders. |
| `header` | `ReactNode`   | no       | The line above the table, where the row goes.  |

## Boundary

The table renders what the plan and the observation already decided. Observing DNS, and deciding
what readiness means for your product, both stay outside it.
