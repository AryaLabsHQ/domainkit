A plan is a snapshot of one zone rendered as exact operations, with a SHA-256 digest over all of
them. Nothing is written while a plan is built: planning is a read.

## Requirements

A requirement is a DNS record your product needs, its conflict `policy`, and an optional `purpose`
the customer sees.

<Snippet file="examples/core/plans.ts" region="requirements" title="Two requirements" />

`policy` defaults to `exclusive` for CNAME and `append` for everything else. An exclusive
requirement means no other record may sit at that name and type; an append requirement tolerates
neighbours.

Every requirement must sit at or below the attached domain. A name outside it fails `InvalidInput`
before the planner reads the zone, so tenants sharing a zone cannot plan into each other's names.

## The four operations

| Operation  | Means                                                                  |
| ---------- | ---------------------------------------------------------------------- |
| `Create`   | The record is missing and will be created                              |
| `Noop`     | An exact match already exists. `ttlDrift` says whether its TTL differs |
| `Conflict` | Incompatible state, with a `reason` for what is in the way             |
| `Delete`   | Cleanup only: remove a record a receipt proves DomainKit created       |

| Conflict reason   | Raised when                                                             | By           |
| ----------------- | ----------------------------------------------------------------------- | ------------ |
| `cname-collision` | A CNAME would share a name with another record, in either direction     | Provisioning |
| `opaque`          | A record at that name and type is one DomainKit cannot model            | Provisioning |
| `exclusive-name`  | An exclusive requirement meets a different record at that name and type | Provisioning |
| `missing`         | The record a receipt names is already gone                              | Cleanup      |
| `value-mismatch`  | The record a receipt names no longer matches what was written           | Cleanup      |

The planner is additive. DomainKit never updates, overwrites, or deletes a record it did not create,
so a conflict is reported and the write does not happen.

<Snippet file="examples/core/plans.ts" region="review" title="What a review screen needs" />

`Plan.renderInstructions(plan)` renders the same operations as copyable lines, for a host whose
customers apply records by hand.

## Approval

An approval binds consent to the plan's digest and to an explicit list of operation ids.

<Snippet file="examples/core/plans.ts" region="approve" title="Approving all of it, or part" />

A plan with conflicts is approved only with `allowPartial` and a conflict-free selection. The digest
ignores `purpose` labels, so relabelling a requirement never invalidates consent the customer
already gave.

Approving an already-approved plan returns the same approval, so a retried request is safe.

## Declining

<Snippet file="examples/core/plans.ts" region="reject" title="Recording a refusal" />

A rejection is terminal for that plan: approving or applying it afterwards fails `Stale`. The domain
itself stays free, so the next plan starts clean.

## Apply

<Snippet file="examples/core/plans.ts" region="apply" title="Applying an approval" />

Apply re-plans the zone before the first write and fails `Stale` when the digest moved, then
revalidates each approved create before writing it. That narrows the race between the last read and
the write; it cannot remove it.

## Receipts

A receipt lists one outcome per operation.

| Outcome   | Carries                                                        |
| --------- | -------------------------------------------------------------- |
| `Applied` | The operation id and the provider's id for the record it wrote |
| `Skipped` | `noop`, `not-approved`, or `not-attempted`                     |
| `Failed`  | The operation id and the provider's message                    |

A failure after a confirmed write is not an exception. Apply stops there, earlier writes stay
`Applied`, later approved operations become `Skipped(not-attempted)`, and the receipt's `status` is
`partial`. Re-planning turns the written records into no-ops and the rest into creates.

A failure before any write marks the attempt `failed` and raises. The next apply re-claims it.

## Three requests, one attempt

Every step is a stored attempt, so a host can render the plan in one request, collect consent in
another, and apply in a third.

<Snippet file="examples/core/plans.ts" region="resume" title="Resuming a flow the customer left" />

| Status     | Means                                                         |
| ---------- | ------------------------------------------------------------- |
| `planned`  | Built and waiting for consent                                 |
| `approved` | Consent recorded, not yet applied                             |
| `applying` | An apply holds the lease                                      |
| `complete` | Every approved write landed                                   |
| `partial`  | A write failed after an earlier one landed; re-plan to finish |
| `failed`   | Apply stopped before any write                                |
| `expired`  | The plan aged out before it was applied                       |
| `rejected` | The customer declined                                         |

A claim while the apply lease is still live fails `Busy`. A plan lives one hour and an apply lease
two minutes by default; `Provision.Policy` changes both.
