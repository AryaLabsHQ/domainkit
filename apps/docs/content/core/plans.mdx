DomainKit treats DNS provisioning as a reviewed transaction, even when the provider API does not offer transactions.

## Lifecycle

| Artifact      | Meaning                                                                             |
| ------------- | ----------------------------------------------------------------------------------- |
| Requirement   | The DNS state your product needs, including ownership and conflict policy           |
| Plan          | A snapshot of `create`, `noop`, and `conflict` operations with an expiry and digest |
| Authorization | Approval for the exact plan digest and selected operations                          |
| Receipt       | What an apply attempt actually changed, including partial outcomes                  |
| Cleanup plan  | A fresh, receipt-bound review of records DomainKit can safely delete                |

Authorization does not make a stale plan safe. Apply rechecks provider state and returns a stale result rather than writing against changed DNS.

## Conflicts

DomainKit is additive and fail-closed:

- an exact record has a `noop` `_tag`;
- a missing record has a `create` `_tag`;
- incompatible state has a `conflict` `_tag`;
- apply never silently replaces the conflicting value.

Partial authorization is opt-in:

```ts
const authorization = await Provisioning.authorize(plan, selectedOperationIds, {
  allowPartial: true,
});
```

## Cleanup

A receipt proves which writes belong to a previous apply. Cleanup creates a new deletion plan from that receipt, then requires authorization for the cleanup digest. If a record drifted, deletion is blocked instead of removing data that DomainKit can no longer prove it owns.

<Callout type="info" title="Persist receipts">
  Receipts are durable lifecycle data. Store them in your primary database; do not rely on a cache
  whose loss would prevent safe cleanup.
</Callout>
