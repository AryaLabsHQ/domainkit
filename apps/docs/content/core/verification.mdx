`Verify.observe` is the only observation operation. It reads the provider through the attachment's
session and the public pool through `Resolver`, stores readiness per requirement, and says when to
look again.

Requirements default to the latest provisioning receipt, meaning the records the apply wrote or
found already in place.

A domain with no attachment is observed too. Public DNS stands alone, no provider evidence is
recorded, and the readiness row is the same shape.

## Three kinds of evidence

| Evidence    | Comes from                                                       | Names      |
| ----------- | ---------------------------------------------------------------- | ---------- |
| `Provider`  | The provider's own record list, through the attachment's session | `provider` |
| `PublicDns` | One recursive resolver, one entry per resolver that answered     | `resolver` |
| `Host`      | Something only your app can see                                  | `source`   |

A provider readback is not propagation. The record can exist at the provider and still be missing
from a resolver, and the two are kept apart so a stuck setup is diagnosable.

Every entry explains itself. `Provider` and `PublicDns` carry `values`, what that source returned
for the requirement's name and type, rendered the way `DnsRecord.data` renders a record and empty
when the source returned nothing. All three carry `detail`, which is `null` when the requirement is
satisfied and otherwise says why it is not: `expected edge.acme.dev; found other.acme.dev`, `no TXT
record at _acme.app.example.com`, `google timed out`.

## Statuses

| Requirement status | Means                                                                   |
| ------------------ | ----------------------------------------------------------------------- |
| `satisfied`        | An exact match was observed                                             |
| `missing`          | Nothing matched                                                         |
| `mismatch`         | An exclusive requirement met a conflicting record at that name and type |
| `unknown`          | No source answered                                                      |

The domain's `overall` is `failed` when any requirement is a mismatch or any host evidence failed,
`ready` when every requirement is satisfied and every host signal is `ok`, and `pending` otherwise.

## The resolver pool

The default `Resolver` fans out to Cloudflare and Google over RFC wire-format DNS-over-HTTPS with a
three-second timeout, and keeps every answer, so readiness can say "found at Cloudflare, missing at
Google". `Resolver.resolve` never fails: a failure or a timeout is a per-resolver outcome.

A wire response counts only when its message id is zero, its single question matches the query in
name, class, and type, it is not truncated, and every answer carries a TTL.

<Snippet file="examples/core/verification.ts" region="policy" title="Quorum and backoff" />

`quorum` decides how many resolvers must agree for `satisfied`: `any` by default, or `all`, or a
minimum. A mismatch at any resolver outranks agreement elsewhere.

## When to look again

<Snippet file="examples/core/verification.ts" region="polling" title="Following the schedule" />

`nextCheckAt` comes from the backoff ladder, 15 seconds, 1 minute, 5 minutes, 30 minutes by default,
measured from when the current pending streak began. The streak restarts when the requirement set
changes and clears when the domain is ready, so a worker sleeps on the readiness row instead of
polling on a timer of its own.
