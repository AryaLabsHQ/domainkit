This guide shows what belongs in your app and what DomainKit handles. Your app owns security,
storage, and product rules. DomainKit handles connecting a provider, planning DNS changes, applying
them, checking the result, and cleaning up.

## Architecture

```text
browser or product client
  -> authenticated host endpoints
  -> host identity, tenant policy, and consent checks
  -> durable connection + plan-attempt + receipt storage
  -> domainkit
  -> Cloudflare, Vercel, or another DnsProvider
```

`@domainkit/react` uses the same boundary through `Transport.Service`:

```text
@domainkit/react
  -> Transport.Service
  -> authenticated host client
  -> the server lifecycle above
```

Provider credentials never cross into the browser transport.

## Decide what is durable

| State                                         | Lifetime                 | Host responsibility                                                               |
| --------------------------------------------- | ------------------------ | --------------------------------------------------------------------------------- |
| OAuth or integration continuation             | Short-lived and one-time | Store until callback consumption; loss may require restarting consent             |
| Provider authorization                        | Durable                  | Persist account context, capabilities, credential reference, and revocation state |
| Encrypted credential                          | Durable and secret       | Encrypt tokens and access-token expiry, restrict access, rotate, and audit use    |
| Organization connection and domain attachment | Durable                  | Bind provider authority to your tenant and an exact discovered provider target    |
| Plan attempt and authorization                | Durable through apply    | Correlate a server-owned plan with the digest the user reviewed                   |
| Apply receipt                                 | Durable                  | Preserve confirmed writes and partial outcomes for later cleanup                  |
| Public-DNS observation                        | Evidence, not authority  | Persist only if your product needs history, polling, or readiness state           |

Do not use a browser store or short-lived cache as the source of truth for provider authorizations,
plans, or receipts.

## 1. Define product requirements on the server

Your product decides which DNS records it needs and why. Check those requirements on the server:

```ts
import { DnsRecord, DomainName } from "domainkit";

const requirement = DnsRecord.Txt({
  metadata: {
    ownership: "product",
    provenance: "domain-onboarding",
    purpose: "domain-verification",
  },
  name: DomainName.parse("_verify.example.com"),
  policy: "append",
  ttl: 300,
  value: "verification-value",
});
```

The browser may display these records, but it must not choose ownership, conflict policy, or provider
authority.

## 2. Implement authorization storage

For an Effect host, provide one `ManagedDnsConnections.Service` for the provider authorization,
encrypted credential reference, organization connections, and domain attachments. An async host implements
`ManagedDnsConnections.AsyncInterface` from the Promise entry point and passes it to
`createDomainKit`:

```ts
import { type ManagedDnsConnections } from "domainkit/promise";
```

A SQL host can save these records in one transaction. If database and vault storage are split, make
the save recoverable behind the same interface.

Use `domainkit/testing`'s in-memory repository in tests only. It does not encrypt credentials or
provide production durability.

PostgreSQL Effect hosts may instead use [`@domainkit/capsuledb`](/docs/reference/capsuledb). The
optional package owns the lifecycle schema and `ManagedDnsConnections.Service`; your application
supplies its existing `PgClient`, calls `Registry.prepare` once at startup, and provides encrypted
credential custody plus tenant/domain bindings. It is intentionally Effect-native: `createDomainKit`
does not initialize CapsuleDB or provide async persistence. An async host must implement
`ManagedDnsConnections.AsyncInterface` (or adapt an Effect service with
`ManagedDnsConnections.toAsync`) and own database startup and disposal.

## 3. Mount provider connection routes

`domainkit/server` supplies one catch-all route program for the shared connection mechanics. In an
async host, pass Promise capabilities to `createDomainKit`:

```ts
import { createDomainKit } from "domainkit/server";

export const domainKit = await createDomainKit({
  baseURL: "https://app.example.com",
  identity: HostIdentity,
  connectionPolicy: HostConnectionPolicy,
  // Each entry implements AsyncInteractiveProvider for one provider/method pair.
  providers: [cloudflareProvider],
  pendingAuthorizations: RedisPendingAuthorizations,
  persistence: ManagedDnsConnections,
});
```

The host owns the persistence implementation, database setup, migrations, and database lifecycle.
DomainKit intentionally does not supply async CapsuleDB persistence.

In an Effect-native host, compose the same capabilities as sibling Layers:

```ts
import { Server } from "domainkit/server";
import { Layer } from "effect";

const DomainKitDependencies = Layer.mergeAll(
  HostIdentityLive,
  HostConnectionPolicyLive,
  ProviderRegistryLive,
  RedisPendingAuthorizationsLive,
  ManagedDnsConnectionsLive,
  CryptoLive,
);

const DomainKitServerLive = Server.layer({
  baseURL: "https://app.example.com",
}).pipe(Layer.provide(DomainKitDependencies));
```

Mount `Server.toWebHandler(DomainKitServerLive).fetch` at `/api/domainkit/*`, or run
`Server.Handler` directly inside an Effect HTTP host. Async frameworks mount `domainKit.fetch` at
the same catch-all route. This handler currently serves only the connection start and callback
routes below; expose provisioning, verification, and cleanup endpoints separately in your app. An
interactive provider connection has two server routes:

1. The start route checks the current user and tenant, asks the host policy to authorize any
   requested existing authorization aggregate, creates a short-lived continuation, and returns a
   provider authorization URL.
2. The callback route trusts the initiating principal stored in the server-side continuation,
   consumes it exactly once, exchanges the provider code, and commits the durable authorization
   aggregate.

A token route validates the submitted credential on the server and commits the same durable
authorization and organization connection without a redirect. Connection start/complete does not
create a domain attachment.

The callback redirects to a previously validated same-origin path. After connection, reconstruct
the provider client from the stored credential and non-secret provider context. Do not ask the
browser to retain the provider token or account client.

Before each OAuth-backed provider operation, load the credential and refresh within a short expiry
skew. Serialize refresh per authorization, reload after acquiring the lock, then persist the entire
rotated credential before restoring the provider session. Terminal OAuth grant failures should
return a reconnect-required product state; transient provider failures should remain retryable.
DomainKit's provider helper performs the exchange, but the host owns this lock-and-persist call
stack.

## Attach an exact provider target

After a connection is returned, load its private aggregate, restore the credential-scoped provider
session, and resolve the requested domain. Persist the selected target with `Connection.attach`:

```ts
import { Connection, DomainName } from "domainkit/promise";

const aggregate = await repository.getByConnectionId(connection.id);
if (aggregate === null) throw new Error("Connection was not persisted");

// Adapt the provider-specific restore helper to your host's ProviderSession.AsyncInterface.
const domainName = DomainName.parse("example.com");
const resolution = await providerSession.resolveTarget(domainName);
if (resolution._tag !== "Resolved") {
  throw new Error("The domain needs an explicit provider-target selection");
}

const attached = await Connection.attach({
  attachment: {
    connectionId: connection.id,
    createdAt: new Date(),
    domain: domainName,
    id: crypto.randomUUID(),
    target: resolution.target,
  },
  connectionId: connection.id,
  ownerId,
  repository,
});
```

The target must come from provider-backed discovery, not browser input. If the result is
`SelectionRequired`, return candidates to the product UI and validate the selected candidate on the
server. Use the focused provider for planning, apply, observation, and receipt-bound cleanup.

## 4. Persist plan attempts before approval

When the user asks to review DNS changes:

1. Load the authorized connection and assert its owner and domain attachment.
2. Reconstruct the provider.
3. Create the plan against an exact zone or a discovered zone.
4. Persist the complete encoded plan, digest, connection, tenant, domain, and expiry as one attempt.
5. Return a browser-safe projection for review.

When the user approves, match the submitted digest to that server-owned attempt before calling
`Provisioning.authorize`. Do not rebuild a plan from browser input and treat it as the reviewed plan.

## 5. Apply once and persist the receipt

Before apply, claim or otherwise lock the plan attempt according to your host's request model. Pass
the saved plan and authorization to `Provisioning.apply`. Store complete and partial receipts before
reporting the outcome.

An apply receipt is more than UI progress. It proves which writes can be considered for a later
cleanup plan.

## 6. Map authenticated endpoints into React

Expose only app-facing operations to the browser, then adapt the client once:

```ts
import { Transport } from "domainkit";

export const transport = Transport.layerFromAsync({
  connection: api.connections,
  provisioning: api.provisioning,
  verification: api.verification,
  cleanup: api.cleanup,
});
```

The React transport carries a `planDigest`; your server can also match an opaque attempt ID in its
session, database, or API route. The transport is an app contract for the browser, not a provider API.

## 7. Keep product readiness separate

`Verification.observe` reports provider and public-DNS evidence for DNS requirements. Your product
may also need service readiness, certificate status, email checks, polling, or a saved onboarding
phase. Keep that product state in the host instead of folding it into DomainKit's observation result.

## Security checklist

- Provider credentials are accepted and used only on trusted server boundaries.
- Every connection, reuse, plan, apply, cleanup, and disconnect route rechecks tenant authority.
- Domain attachments are checked in addition to provider scopes.
- Interactive continuations are single-use and bound to the initiating flow.
- OAuth refresh is serialized, persisted before use, and falls back to reconnect only for terminal grants.
- Plans and cleanup plans are authorized by exact digest.
- Partial receipts are stored before a retry or remediation path begins.
- Detaching one domain does not imply deleting DNS records.
- Final-binding revocation remains retryable until the provider confirms it.
