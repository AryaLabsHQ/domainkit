You will connect a fake provider, build a plan for two DNS requirements, approve its digest, apply
it, and observe the result. No provider account, network request, database, or browser is involved.

## Prerequisites

- Node.js 24.10 or newer, or Bun 1.4 or newer.
- A TypeScript project using ESM.

## Install

```package-install
domainkit effect@rc
```

`effect` is a peer dependency. The package root is Effect-native and this tutorial uses it at every
step.

## What you just read

`Provision.plan` listed the zone and reconciled it against the two requirements. The fake provider
already holds the TXT record, so the plan carries one `Create` for the CNAME and one `Noop` for the
TXT, plus a digest over both.

`Provision.approve` recorded consent for that digest. `Provision.apply` re-planned the zone, saw the
digest had not moved, wrote the CNAME, and returned a receipt whose `outcomes` name one `Applied`
and one `Skipped` with reason `noop`.

`Verify.observe` read the provider through the connection and public DNS through the resolver, and
stored per-requirement readiness with a `nextCheckAt` for the next look.

## The moving parts

| Piece                   | What it is here                                                       |
| ----------------------- | --------------------------------------------------------------------- |
| `Testing.provider`      | A provider definition over in-memory zones, with a token method       |
| `DomainKit.layerMemory` | Every lifecycle service, memory storage, and a throwaway custody key  |
| `Principal.Service`     | Who is acting. Every stored row is scoped by it; there is no default  |
| `Connect.start`         | Connects the provider and attaches the domain in one call for a token |

## Run it again

Run the program a second time. The plan now carries two `Noop` operations, `Plan.isApplicable` is
`false`, and there is nothing to write. Planning is a read, so it is safe to run whenever a screen
needs to show what would change.
