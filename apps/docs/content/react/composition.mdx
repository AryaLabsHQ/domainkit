Complete flows are built from smaller parts. Every public part accepts Base UI's `render` prop plus
state-aware `className` and `style` values. `Connection.Flow` and `Connection.ConnectTrigger` are
ready-made styles. `Connection.Trigger` is the unstyled trigger primitive; its `children` supply
the label and `render` lets you use your own button. Use `ConnectTrigger` when you want the
provider-marked trigger that opens the dialog.

```tsx
<Connection.OAuthAction
  controller={controller}
  label="Connect"
  render={<MyButton variant="primary" />}
/>
```

The [Host connection](/components/host-connection) page owns the complete controller, trigger, and
dialog example together with its API tables.

## Theming

```tsx
<DomainKit.Root
  colorScheme="inherit"
  icons={{ copy: <Copy />, copied: <Check />, download: <Download /> }}
  marks={{ internaldns: <InternalDnsMark /> }}
  messages={{ connectProvider: (name) => `Connect ${name}` }}
  theme={{ accent: "var(--brand-primary)", radius: "var(--radius-md)" }}
  transport={transport}
>
  {children}
</DomainKit.Root>
```

The opt-in stylesheet reads `--domainkit-*` variables. Theme props set those variables without
replacing the host font, colors, or icons.

Recognized provider marks load from `integrations.sh` and fall back to the provider's first letter
when unavailable. Use `marks` when your product needs to replace a remote mark or supply branding
for a private provider.

## Host notifications

DomainKit emits lifecycle events after user-initiated changes. Keep notification UI in the host app
and map the events to Sonner, another toast system, telemetry, or nothing:

```tsx
<DomainKit.Root
  onEvent={(event) => {
    switch (event._tag) {
      case "ConnectionEstablished":
        toast.success(`${event.connection.provider.name} connected`);
        break;
      case "RecordsApplied":
        toast.success("DNS records added");
        break;
      case "RecordsCleaned":
        toast.success("DNS records removed");
        break;
      case "DomainDetached":
        toast.success("Domain detached");
        break;
    }
  }}
  transport={transport}
>
  {children}
</DomainKit.Root>
```

Partial apply and cleanup results have their own events, so hosts can show a warning instead of
reporting partial work as success. Initial inspection and passive verification do not emit events.

The default dialogs close after a complete success. Partial results and failures stay visible because
they need user attention; short success messages belong to the host.

## Records from parts

Record parts accept browser-safe records directly and do not require
`DomainKit.Root` or a transport. The [Records](/components/records) page owns the table, zone-file,
copy-control, and API examples.

## Effect Atom models

Every stateful lifecycle exposes the atoms used by its controller and flow:

```tsx
const model = Provisioning.useModel(connection, records);
const state = useAtomValue(model.state);
const command = useAtomSet(model.command);

if (state._tag === "Review") {
  const isNoopOnly = state.plan.operations.every((operation) => operation._tag === "Noop");

  return (
    <Operations.Root lifecycle="provisioning">
      {state.plan.operations.map((operation) => (
        <Operations.Item key={operation.id} operation={operation} />
      ))}
      {isNoopOnly ? (
        <p>No changes needed</p>
      ) : (
        <button onClick={() => command(Provisioning.Command.Apply())}>Apply approved plan</button>
      )}
    </Operations.Root>
  );
}
```

The same model interface is available as `Connection.useModel`, `Verification.useModel`, and
`Cleanup.useModel`. `Operations.List` is the full neutral operation view; its parts support Base UI
render elements, forwarded refs, state-aware classes, and host event handlers.
