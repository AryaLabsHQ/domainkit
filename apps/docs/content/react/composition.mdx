`Domain.Flow` renders four slots, and every one has a default. Replacing a slot changes that part
and nothing else.

| Slot           | Receives                                        | Default                                                    |
| -------------- | ----------------------------------------------- | ---------------------------------------------------------- |
| `connection`   | `{ controller, domain }`                        | `Connect.Card` once connected, `Connect.Dialog` until then |
| `records`      | `{ records, readiness, controller, domain }`    | `Records.Table`                                            |
| `verification` | `{ controller, domain }`                        | `Verify.Status` with per-requirement evidence              |
| `actions`      | `{ connection, provisioning, cleanup, domain }` | Review changes, Approve, Decline, Remove records           |

## Your own layout

`Domain.Flow` adds no layout container around a slot: its output is a direct child of the flow root,
so a grid on the flow places the slots directly without `display: contents`.

## Parts

Every rendered element is a part. A part takes its element's own props plus three composition props.

| Prop        | Takes                                                            |
| ----------- | ---------------------------------------------------------------- |
| `className` | A string, or a function of the part's state                      |
| `style`     | A `CSSProperties`, or a function of the part's state             |
| `render`    | An element or render function that replaces the element outright |

Parts also carry `data-domainkit-part` and, where they have one, a state attribute, so a stylesheet
can target them without a class name.

Every dialog and popover takes a `render` prop of its own that replaces the surface, so a host with
its own dialog primitive keeps its dialog and DomainKit's behaviour.
