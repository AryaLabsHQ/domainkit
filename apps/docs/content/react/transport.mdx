`domainkit/client` is the browser's view of the routes you mounted. It holds no credential and knows
no provider: it calls your server, and your server calls the provider.

```text
@domainkit/react -> Transport.fromFetch -> your routes -> domainkit/server -> provider
```

## Build one

<Snippet file="examples/client/transport.ts" region="create" title="Over the mounted routes" />

The base URL is the prefix the route group is mounted at. A relative path is fine when the app and
the API share an origin.

<Snippet file="examples/client/transport.ts" region="headers" title="With host headers" />

`headers` is a `HeadersInit` or a function returning one, awaited per request, so a token your app
refreshes is read at call time rather than captured once.

Cookies are the usual answer instead. The provider callback is a top-level navigation, so a host
whose `Identity` reads a cookie needs no headers here at all.

## Capability groups

<Snippet file="examples/client/transport.ts" region="capabilities" title="Declaring what exists" />

| Group          | Methods                                                          |
| -------------- | ---------------------------------------------------------------- |
| `connection`   | `inspect`, `discover`, `start`, `attach`, `detach`, `disconnect` |
| `provisioning` | `plan`, `approve`, `reject`, `apply`, `attempt`                  |
| `verification` | `observe`                                                        |
| `cleanup`      | `plan`, `approve`, `reject`, `apply`                             |

Every group is optional. A host that mounts only the connection routes gets a transport that
typechecks and a UI that renders only the connection step, because `@domainkit/react` reads
`Transport.capabilities(transport)` and skips the rest.

## Calling it

<Snippet file="examples/client/transport.ts" region="call" title="From Effect" />

<Snippet file="examples/client/transport.ts" region="promises" title="From Promises" />

Every method returns `Effect<A, DomainKit.Error>` with no requirements, so `@domainkit/react` runs
them without an Effect runtime in the tree. `Transport.toAsync` gives the same methods as Promises
that reject with the same error.

`Transport.fromAsync` goes the other way, for a host whose client is already Promise-shaped.

## Failures

A failure arrives as the `DomainKit.Error` the lifecycle raised, reason intact, so a `Conflict`
still carries its conflicting operations and the UI can list them.

A reply the transport cannot read as one came from in front of your server. It is classified from
the status instead, and every result names the transport's base URL, so a proxy answering HTML is
obvious in the message.

| Status        | Becomes                                                                  |
| ------------- | ------------------------------------------------------------------------ |
| 401           | `Unauthenticated`                                                        |
| 403           | `Forbidden`                                                              |
| 409           | `ProviderConflict`                                                       |
| 429 and 5xx   | `ProviderUnavailable`, retryable, with `retryAfterMs` from `retry-after` |
| anything else | `ProviderRejected`, carrying the status as its code                      |

## In tests

<Snippet file="examples/testing/fakes.ts" region="transport" title="A transport for UI tests" />

`Testing.transport` runs `domainkit/server` over memory storage and a fake provider in the same
process, so a component test drives the real lifecycle instead of a stub.

The [`domainkit/client` reference](/docs/reference/transport) lists every method on every group.
