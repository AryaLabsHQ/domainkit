Use `domainkit/promise` in route handlers and other app code that uses Promises instead of Effect
values.

```ts
import { DnsRecord, DomainName, Provisioning } from "domainkit/promise";

const requirement = DnsRecord.Cname({
  metadata: { ownership: "customer", provenance: "example", purpose: "routing" },
  name: DomainName.parse("app.example.com"),
  policy: "exclusive",
  target: DomainName.parse("tenant.example.net"),
  ttl: 300,
});

const result = await Provisioning.create({
  provider,
  requirements: [requirement],
  target: Provisioning.Target.ExactZone({ zone: "example.com" }),
});
```

The Promise facade uses the same callable constructors as the Effect entry point. Use
`DnsRecord.Txt(...)`, `DnsPlan.Operation.create(...)`, and provider helpers such as
`Vercel.AccountContext.team(...)` for trusted values; use the exported schemas when decoding
serialized data.

`VERSION` reports the installed package version.

The Promise API accepts Promise-based provider and resolver interfaces and runs the same Effect
programs internally. Results, tagged outcomes, plan digests, and failures match the core package.

## Boundary rule

Choose one programming model per app layer. Do not convert Effect to Promise and back through the
same lifecycle. If the app core uses Effect, call `Effect.runPromise` once at the framework boundary.
If the host uses Promises, use this entry point consistently.

For browser UI, implement the narrower [application transport](/docs/reference/transport) rather
than sending the Promise provider object to the client.
